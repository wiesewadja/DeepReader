# 📚 DeepReader 核心技术架构方案 (v2.0 认知状态机版)

## 一、 架构设计哲学：从“自由探索”到“确定性流水线”

本系统彻底摒弃了传统 ReAct Agent（让大模型自主决定调用什么工具、何时结束）带来的幻觉、死循环和 Token 浪费问题。

我们将整个 AI 的思考过程交由 **TypeScript 代码（总指挥）** 进行强控编排。大模型不再是拥有自由意志的“黑盒”，而是流水线上在不同状态节点（State Node）被反复唤醒的“极致单项专家”。



---

## 二、 核心中枢：五步认知状态机 (The Cognitive States)

系统包含 1 个路由节点和 4 个递进的认知处理节点。每个节点都有**固定的系统提示词（System Prompt）**，以最大化触发 LLM 的 Prompt Caching（提示词缓存），实现降本增效。

### 🔘 S0: 意图路由器 (The Router)
* **角色设定**：极速分类器（分拣帽）。
* **选用模型**：`gpt-4o-mini` 或其他极速低成本模型。
* **输入/输出**：输入用户原始 `query`；强制输出 JSON 格式 `{"depth": 0|1|2|3, "reason": "..."}`。
* **核心动作**：判断用户提问属于艾德勒阅读法的哪一个层次，决定后续状态机的流转深度。

### 🟢 S1: 检视阅读站 (Inspectional State)
* **艾德勒映射**：了解骨架，圈定战区。
* **调用工具**：`get_toc` (获取目录大纲) 或 `search_doc_global` (全局泛搜)。
* **核心动作**：不深究逻辑，只为了获取关联的章节范围（`node_id`）或跨书本的书单。
* **状态输出**：目标战区数组，如 `[{book: "麦肯锡", node_id: "c4"}, ...]`。

### 🟡 S2: 分析阅读站 (Analytical State) - *循环节点*
* **艾德勒映射**：词汇共识与逻辑解构。
* **调用工具**：`search_doc` (强制带入 S1 提供的 `node_id` 锁定范围)。
* **核心动作**：这是针对单书/单章节的微观解构。
  1. **查词义**：强制大模型先查明核心概念的原本定义。
  2. **提逻辑**：基于该定义，提取作者论证的“前提、步骤、结论”。
* **状态输出**：纯净的生肉逻辑数据块（附带 `^block_id`）。

### 🔴 S3: 主题与批判站 (Syntopical & Critical State)
* **艾德勒映射**：客观评判、建立共通词汇、梳理争议。
* **调用工具**：**无（物理剥夺搜索工具）**。
* **核心动作**：大模型接收 S2 传来的多份“生肉逻辑”，执行跨视角的概念翻译（Semantic Alignment）和逻辑漏洞审查。
* **状态输出**：高维度的统合洞见（文字描述）。

### ✨ S4: 知识交付站 (The Formatter)
* **角色设定**：昭先生的专属知识助理（奚童）。
* **调用工具**：**无**。
* **核心动作**：将上游传来的数据，严格按照用户的排版偏好转化为 Markdown，并将生肉数据中的 `^block_id` 转换为 Obsidian 原生双链格式 `[[书籍名#^block_id|自然文本]]`。
* **状态输出**：最终的流式 (Stream) 响应。

## 三、 主控调度流：累加式动态路由 (Cumulative Routing)

TypeScript 的主函数是整个系统的“监工”。它根据 S0 返回的 `depth`，决定电梯在哪些楼层停靠。上一个状态的输出，将直接作为下一个状态的上下文变量。

```typescript
// DeepReader Engine 核心主控流 (伪代码)
// engine.ts

export async function deepReaderEngine(userQuery: string) {
    ui.setStatus("🌀 正在研判问题深度...");
    
    // 1. 路由器：只做一件事，拿到深度 (0, 1, 2, 3)
    const depth = await runState_0_Router(userQuery); 
    
    let rawDataToFormat = null;

    // 2. 策略分发：根据深度，进入专属的“任务舱”
    switch (depth) {
        case 0:
            // 【日常闲聊舱】
            rawDataToFormat = "这是一个日常交互，无需查书。请用奚童的口吻得体地回复。";
            break;

        case 1:
            // 【检视阅读舱】：只关心宏观大纲
            ui.setStatus("🗺️ 正在扫描书籍宏观框架...");
            rawDataToFormat = await executeTask_Inspectional(userQuery);
            break;

        case 2:
            // 【分析阅读舱】：死磕特定概念与微观逻辑
            ui.setStatus("🔍 正在与作者达成共识并解构逻辑...");
            rawDataToFormat = await executeTask_Analytical(userQuery);
            break;

        case 3:
            // 【主题阅读舱】：跨越书籍边界的高维统合
            ui.setStatus("⚔️ 正在进行高维概念缝合与辩证...");
            rawDataToFormat = await executeTask_Syntopical(userQuery);
            break;
            
        default:
            throw new Error("未知的阅读深度！");
    }

    // 3. 终极汇总：无论经历了哪个舱的折腾，最终统一步伐，交给 S4 知识交付官
    ui.setStatus("📝 正在排版双链笔记...");
    return await runState_4_Formatter(rawDataToFormat, userQuery);
}


// tasks.ts - 深度 2 的专属任务舱
async function executeTask_Analytical(userQuery: string) {
    // 步骤 2.1：(隐性检视) 先去库里精准定位这道题属于哪个章节
    const targetNodeId = await findRelevantChapter(userQuery); 
    
    // 步骤 2.2：(词义澄清) 限定在这个章节内，查明概念定义
    const termDefinition = await runState_Clarifier(userQuery, targetNodeId);
    
    // 步骤 2.3：(逻辑解构) 基于定义，抠出逻辑链条
    const logicChain = await runState_Extractor(termDefinition, targetNodeId);
    
    // 把生肉数据打包返回，喂给 S4
    return `
      【核心概念定义】：${termDefinition}
      【作者推演逻辑】：${logicChain}
    `;
}

// tasks.ts - 深度 3 的专属任务舱
async function executeTask_Syntopical(userQuery: string) {
    // 步骤 3.1：全局大撒网，拿到多本书的相关段落（自带 ^block_id）
    const globalPassages = await searchGlobalLibrary(userQuery);
    
    // 步骤 3.2：概念对齐与辩证分析
    const dialecticInsight = await runState_Dialectic(globalPassages, userQuery);
    
    return `
      【跨书本素材】：${JSON.stringify(globalPassages)}
      【统合洞见】：${dialecticInsight}
    `;
}
```

## 四、 后端 RAG 引擎的配套升级 (Python 端)

为了支撑前端极其克制且精准的 S1 和 S2 节点，后端的向量化处理必须达到外科手术级别。



1. **滑动窗口切分 (Overlap)**：
   * 废弃生硬的字数切分。相邻 Chunk 必须保留 15% 左右的上下文重叠，防止“指代代词（如：这个方法）”的语义断层。
2. **Small-to-Big 检索策略**：
   * 入库时：将完整物理段落（Parent）拆分为多句（Child）分别进行 Embedding。
   * 检索时：匹配到 Child，但后端强行返回整个 Parent 段落给大模型，确保 S2 节点有充足的逻辑上下文。
3. **元数据标签注入 (Metadata Enrichment)**：
   * 离线预处理阶段，调用小模型为每个 Parent Chunk 提取核心词（或利用 Regex 提取高亮、加粗词），拼接到文本开头后再进行向量化，大幅提升召回率。
4. **意图动态加权 RRF (Intent-based Weighting)**：
   * 接受前端 S0 的意图参数。遇到短概念搜索放大 Vector 权重；遇到特定数字/事实搜索放大 BM25 权重。

## 五、 UI / UX 极致极客体验 (Obsidian 前端)

利用单向状态机的“步骤确定性”，在 Obsidian 侧边栏/对话框中渲染骨灰级的步骤感知动画：

1. **状态指示器组件**：通过监听 TypeScript 的状态流转，前端按顺序点亮步骤条。
   * `[✓] 检视完毕 (耗时 0.4s)`
   * `[✓] 词汇共识：锁定“系统边界”定义 (^ch4-p12) (耗时 1.1s)`
   * `[✓] 逻辑解构：提取出 2 个前置条件 (耗时 1.5s)`
   * `[✨] 正在排版交付...`
2. **沉没成本回收 (优雅降级)**：
   * 即使 S2 在特定 `node_id` 下未能查到逻辑，系统绝不抛出 Error，而是将“未能找到原书逻辑”的状态传递给 S4。S4 将生成一段得体的回复：“在第四章中未能找到相关推演，以下是作者在全书中的散落观点...”，情绪价值拉满。

## 六、 架构核心优势总结

1. **零幻觉与零死循环**：通过剥夺大模型的工具调度自由，在 S4 排版阶段给它极其纯净的数据，彻底消灭格式错乱和事实编造。
