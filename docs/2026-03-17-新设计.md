

# 🚀 DeepReader 极速架构蓝图：基于《如何阅读一本书》的智能 RAG 方案

## 用户意图识别

我们将《如何阅读一本书》的分层阅读法，转化为 4 个维度的正则特征库。在 TypeScript 中，我们可以这样设计这套规则引擎：

1. 意图特征库设计 (Intent Regex Dictionary)
我们可以把用户的提问拆解为 4 个核心维度，每个维度对应一组正则和需要分配的工具：

TypeScript
// router.ts

// 1. 宏观意图：检视阅读 (全局)
// 目标：只要涉及全书的概括，绝对不给全文检索工具。
const MACRO_REGEX = /(总结|大纲|概括|全书|核心观点|讲了什么|总体结构|主旨|脉络|框架|读后感|核心思想)/i;

// 2. 定位意图：分析阅读 (精准抓取)
// 目标：用户明确指出了特定的章节，直接给提取章节的工具。
const LOCATE_REGEX = /(第[0-9一二三四五六七八九十百]+[章|节|部分|页]|引言|结语|附录)/i;

// 3. 跨书意图：主题阅读 (全局联邦)
// 目标：用户想对比不同文献。
const SYNTOPICAL_REGEX = /(对比|结合|另一本|异同|其他书|不同文献|主题阅读|联系起来)/i;

// 4. 动作意图：输出控制 (画图、写卡片)
// 目标：控制输出格式的特殊工具。
const ACTION_REGEX = /(画|思维导图|脑图|图表|表格|总结成表格|做(个|张)卡片|闪卡|写(篇|个)笔记)/i;

2. 核心路由函数 (The Router Function)
有了特征库，我们就可以写一个极其快速的路由函数。这个函数的巧妙之处在于：它采用**“叠加赋权”**的逻辑，而不是非黑即白的互斥。

TypeScript
export function determineReadingStrategy(userInput: string) {
    // 默认的基础工具包 (假设你的基础工具包含技能平台读取等)
    const tools = new Set<string>();
    const intents: string[] = [];

    // --- 步骤 1：探测跨书意图 ---
    if (SYNTOPICAL_REGEX.test(userInput)) {
        intents.push("【主题阅读（跨文档）】");
        tools.add("search_read_books"); // 跨书检索工具
        // 如果是跨书，通常不需要单书的大纲
    }

    // --- 步骤 2：探测宏观/微观意图 ---
    const isMacro = MACRO_REGEX.test(userInput);
    const isLocate = LOCATE_REGEX.test(userInput);

    if (isMacro && !isLocate) {
        // 纯宏观：比如“总结全书”
        intents.push("【检视阅读（宏观总结）】");
        tools.add("get_toc"); // 只给大纲工具，拦截 search_doc
    } 
    else if (isLocate) {
        // 定位阅读：比如“总结第三章”、“第三章讲了什么”
        intents.push("【分析阅读（特定章节定位）】");
        tools.add("get_toc");     // 用于确定第三章的 node_id
        tools.add("get_chapter"); // 用于直接拉取该章全文
        // 可选：如果不确定具体讲什么，加上 search_doc
    } 
    else if (!SYNTOPICAL_REGEX.test(userInput)) {
        // 默认兜底：微观细节检索（比如“什么是MECE原则？”）
        intents.push("【分析阅读（微观检索）】");
        tools.add("search_doc"); 
    }

    // --- 步骤 3：探测动作输出意图 ---
    if (ACTION_REGEX.test(userInput)) {
        intents.push("【动作控制（制图/格式化）】");
        if (userInput.includes("导图") || userInput.includes("画")) {
            tools.add("excalidraw");
        }
        if (userInput.includes("卡片") || userInput.includes("笔记")) {
            tools.add("write_note");
        }
    }

    // --- 步骤 4：生成动态尾部指令 (Dynamic Suffix) ---
    const systemNote = `
<system_note>
【Router 强制路由】
系统已判定用户的实际意图包含：${intents.join(', ')}。
你当前仅被允许使用以下工具：[${Array.from(tools).join(', ')}]。
严禁使用其他未列出的工具。请基于提供的工具直接执行任务。
</system_note>
`;

    return {
        allowedTools: Array.from(tools),
        systemNote: systemNote
    };
}
3. 应对高频“对抗性测试”（Edge Cases）
用这套正则，我们来测试几个用户极其容易问出的“刁钻”问题，看看 Router 是怎么优雅化解的：

测试案例 A：“画一个全书的思维导图。”

命中： MACRO_REGEX (全书) + ACTION_REGEX (思维导图)。

分配工具： ['get_toc', 'excalidraw']。

效果： 完美。大模型绝不会去全文搜索，而是直接拉大纲，然后画图。

测试案例 B：“帮我总结一下第3章，里面提到的那个手机厂商的例子重点说一下。”

命中： MACRO_REGEX (总结) + LOCATE_REGEX (第3章)。

分配工具： ['get_toc', 'get_chapter']。（因为命中了具体章节，即便有总结字眼，也不视为“全书总结”）。

效果： 完美。大模型知道要去拿第 3 章的原文，而不是仅仅看全书摘要。

测试案例 C：“什么是‘第一天的答案’？”

命中： 啥都没命中（没有宏观、跨书、画图、章节字眼）。

分配工具： 兜底策略 -> ['search_doc']。

效果： 完美。大模型乖乖拿着这个词去向量数据库里做精确匹配。

总结与进一步优化
这套正则匹配的好处是速度极快（0毫秒级延迟），而且能拦截掉 95% 以上导致大模型“发疯”的错误工具调用。

在实际投产时，如果你发现用户有时说话比较模糊，正则抓不准，你可以引入一个**“兜底重路由机制（Fallback Re-routing）”**：
如果分配了 search_doc，但大模型连续 2 次返回 Observation: 未找到结果，你在前端代码里强制抛出一个中断，提示大模型：“search_doc 失败，请向用户提问以明确意图，或调用 get_toc 查看是否存在该内容。”


## 模块二：极速检索策略 (前后端配合)
彻底消灭大模型“猜关键词”的盲目 ReAct。

1. **宏观检索（前端本地解决）：**
   * 针对“总结全书”、“画思维导图”等宏观意图。
   * **动作：** 拦截请求，不走向量库。直接读取本地的 Pageindex JSON，把章节标题和 `summary` 拼接后喂给大模型。
2. **微观检索（后端 Small-to-Big 机制）：**
   * 针对“解释特定概念”、“找具体案例”等细节意图。
   * **动作：** 前端调用后端的 `search_doc` API。后端向量命中某个 `node_id` 后，**向外扩展**，把该段落的“上一段”和“下一段”一并拼装返回。
   * **返回格式：** 明确标识出锚点，例如 `🎯核心命中: ^0042`，连同上下文一起发给前端。

## 模块三：意图路由与成本控制 (Frontend Agent)
解决 14 个工具导致的幻觉，同时完美命中 LLM 的 **Prompt Caching（提示词缓存）** 机制。

1. **静态前缀 (Static Prefix)：最大化缓存命中率**
   * 把最占 Token 的内容锁死在 System Prompt 的最前面，**绝对不在多轮对话中动态修改它们**。
   * 静态内容包括：14 个工具的完整 JSON Schema、当前书籍的全局摘要、大模型的人设和通用规则。
2. **意图嗅探器 (Intent Router)：**
   * 用户提问时，前端用轻量正则或极小模型（如 Flash），瞬间判断意图处于《如何阅读一本书》的哪一层：
     * **检视阅读 (宏观)：** 只准用 `get_toc`。
     * **分析阅读 (微观)：** 准用 `search_doc`。
     * **主题阅读 (跨书)：** 准用 `search_read_books`。
     * **输出/制图：** 准用 `excalidraw`, `write_note`。
3. **工具动态尾部注入 (Dynamic Suffix Steering)：**
   * 将 Router 的判定结果，伪装成系统指令 `<system_note>`，**悄悄拼接在用户当次提问的开头**。
   * *示例：* `<system_note>当前为【检视阅读】意图，严禁使用全文检索，请调用 get_toc 工具获取摘要。</system_note> 用户的提问：帮我总结这本书。`

## 模块四：终极系统提示词 (System Prompt)
这是锁死在“静态前缀”里的灵魂规则，强制大模型输出优雅的 Obsidian 双链。


```markdown
# Role: DeepReader Agent
你是一个运行在 Obsidian 中的顶级 AI 阅读与知识管理助手。你精通《如何阅读一本书》中的分层阅读法。

# Context (当前环境)
- 当前阅读书籍：《{{book_name}}》
- 常驻全书摘要：{{book_summary}} (约 500 字)

# 🧠 Core Strategy (核心行为准则)
1. 【路由服从】：每次对话前，系统会通过 `<system_note>` 告诉你当前属于哪种阅读层级（检视/分析/主题），你必须**绝对服从**该限制，仅调用被允许的工具。
2. 【防死循环熔断】：如果调用的搜索工具连续 2 次未返回有效结果，**必须立即停止调用**，向用户承认未找到，或建议查看大纲。严禁无限重试！

# 📝 Obsidian Wiki-link Embedding Rules (行内自然引用规范)
你的回答必须完美融入用户的个人知识库。当你根据工具返回的【核心锚点】(如 `^0042`) 回答问题时：
1. **语法约束：** 必须使用 Obsidian 别名链接语法 `[[书籍名称#核心锚点|自然展示文本]]`。
2. **无缝行内嵌入：** 引用必须充当句子中的主语、宾语或修饰语，严禁像打补丁一样生硬地堆砌在句末。
3. **正确范例：** 面对时间紧迫的汇报，你可以尝试使用著名的[[麦肯锡方法#^0042|电梯陈述法]]，强迫自己在30秒内传递核心洞见。
4. **错误范例 (绝对禁止)：** 如果汇报时间短，你要在30秒内说清楚。[[麦肯锡方法#^0042]]
```

## 模块五：多轮对话记忆清理 (Memory Garbage Collection)
防止上下文爆炸和 AI 精神分裂的最后一道防线。

* **动作：** 在一轮 ReAct 循环彻底结束，并且 Agent 吐出了最终的回答（Final Answer）给用户后，你的插件底层必须执行“大扫除”。
* **清洗逻辑：** 遍历本次对话的 `messages` 数组，**无情地删掉**中间所有的 `Thought`、`Tool Call` 和 `Tool Response`。
* **保留结果：** 长期记忆中，只留下干干净净的 `{"role": "user", "content": "问题"}` 和 `{"role": "assistant", "content": "带双链的精美回答"}`。下一次提问时，带着这个干净的记忆去请求大模型。
