## S2-Pre 在状态机中的位置 (position)

```
S0 Router ──► S1 Inspectional ──► S2-Pre ──► S2 Analytical (走 ReAct)
                                  (本节点)  ╰─► S4 Formatter (早停)
```

**S2-Pre 解决的核心问题**：S1 只看了目录摘要就锁定了 scope——**摘要是有损的**。关键词不出现在摘要里就会导致整章被误排除。S2-Pre 在**进入昂贵的 ReAct 工具循环之前**，先用搜索来"补救"scope 选得不准的问题，并尝试在质量足够时**跳过后续分析直接出答案**。

---

## 核心问题：S2-Pre 解决什么 (why)

| 痛点 | S2-Pre 怎么解 |
|---|---|
| S1 摘要没提到关键词 → scope 漏章 | 预检索用关键词召回，命中节点强制纳入 scope |
| 用户问 5 段细节问题 → 不需要 ReAct | 预检索命中质量够高 → 早停直接答 |
| S2 上一轮说"书里没 X" → 实际有 | L5 负向声明复核 → 强制 S2 重跑 |
| 反复搜同样 block_id 浪费 token | `prevSearchedBlockIds` 合并 |

## 执行流程：5 步 + 1 旁支 (flow)

### 1. Scope 验证 (`validateScopeNodeIds`)

读 `tree.json`，把 S1 传下来的 `scopeNodeIds` 跟实际树里的 nodeId 做交集——S1 选了不存在的 id 就被剔除。同时拿 `nodeFileMap` 备用。

### 2. Scope Hard-Guard (`enforceScopeHardGuard`)

**"scope 守卫"**——三道保险：

1. **用户当前阅读章节**（`currentNodeId`）**必须**在 scope 里
2. **用户在消息里显式引用的章节**（`[[24 - xxx]]` 形式）**必须**在 scope 里
3. LLM 推断的 scope 保留原顺序

S1 和 S2-Pre 都跑同一份代码（**单一收尾点**）——避免两层行为漂移。

### 3. L5 负向声明自动复核（旁支 1）

**针对"幻觉修复"的关键设计**：

```
上一轮 S2 答："书中未出现 X"
    ↓ 检测 analysisResult 中是否有 "未出现/未提及/没有提到/书里没有/并未提及"
    ↓
对全量书库（不受 scope 限制）做一次 searchBookV2
    ↓
如果 score > 0.3 找到证据 → 强制 S2 重跑，把证据注入到 S2 的 prompt
```

**为什么不直接 patch S4 的 prompt？** 代码注释里讲得很清楚——历史上"24章 / 回报函数工程"案例：即使给了正确证据，S4 formatter 仍然会自信地说"未出现"。**只有让 S2 用 ReAct 工具循环重新分析，才能根本性修正**。

### 4. 预检索 RRF

**关键设计**：

- **关键词来源**：用 S1 产出的 `suggestedKeywords`（不是用户原 query，也不是 betterQuestion）
- **去重 + 限流**：`[...new Set(...)].slice(0, 5)`——S1 可能产生重叠关键词，最多用 5 个
- **并行检索**：`Promise.all(5 keywords.map(searchBookV2))`
- **节点级融合（手工 RRF）**：
  ```typescript
  let score = baseScore + hitCount * 0.1;  // 被多个关键词命中加分
  if (currentNodeId) score += 0.2;          // 当前阅读章节再 +0.2
  ```
- **封装成 RunnableLambda** 挂在 LangGraph `callbacks` 上——trace 可见

### 5. 早停决策

详见下一节。

### 6. 走正常 S2 路径

把命中作为 `<pre_search_results>` 块注入 S2 的 prompt，把命中的 `block_ids` 合并到 `prevSearchedBlockIds`——S2 后续 ReAct 循环不会重复搜这些块。

## 早停决策：四道闸门 (gates)

**全部通过**才早停：

| 闸门 | 阈值 | 作用 |
|---|---|---|
| ① 加权分数 | `wScore = top1×0.6 + top2×0.3 + top3×0.1 ≥ earlyStopThreshold`（默认 0.6） | Top-1 主导的质量 |
| ② 结果数量 | `hits.length >= 2` | 避免单条偶然高分的"假阳性" |
| ③ 实质性分数 | `substantiveScore ≥ 30` | 块是否有真实内容（非空标题） |
| ④ 不被 L5 强制 | `!l5ForcesAnalytical` | L5 找到证据就不能早停 |

`substantiveScore` 的计算（100 分制）：

```typescript
if (b.block_id) s += 20;                      // 有真 block_id
s += Math.min(b.content.length / 10, 30);    // 文本长度（封顶 30）
if (b.content.length > 20) s += 15;          // 非空壳
```

**如果早停**：

- 调 `buildEarlyStopPrompt` 拼一个**直接出答案**的 prompt
- 调 `mainModel.invoke(...)` 一次——**不走 ReAct 循环**
- 调 `verifyAndCleanContent` 做输出清理（除掉 LLM 幻觉生成的 block_id）
- `earlyStopContent = 'done'`（路由信号）→ `routeAfterPreSearch` 看到直接走 Formatter

**如果走正常路径**：

- 把命中作为 `<pre_search_results>` 块注入 S2 的 prompt
- 把命中的 `block_ids` 合并到 `prevSearchedBlockIds`——**S2 后续 ReAct 循环不会重复搜这些块**

### 路由层的两个"强制走 S2"信号

`routeAfterPreSearch` 有两个独立 override：

```typescript
if (state.correctionDetected) → analytical         // 用户反驳了上一轮
if (state.verifiedFullBookHits.length > 0) → analytical  // L5 找到证据
if (state.earlyStopContent) → formatter            // 早停
return analytical                                  // 默认
```

## 6 个已知问题（故障地图）(issues)

> 以下基于 codegraph + 源码静态分析。**未做运行验证**，影响评级为 [INFERENCE]。
> **修复路径**见 [§ 建议的修复路径](#future)。

### **问题 1 (CRITICAL)：`wScore` 数值含义不稳定，阈值 0.6 是无意义的硬编码**

**症状**：`wScore >= 0.6` 决定早停，但 `0.6` 实际可能被各种条件改写。

**根因**：`BookSearchResultV2.score` 是 `fusedScore`，最终是 `levelWeight × fusedSignal`：

```typescript
// vault/search.ts:271
const score = candidate.score * recallWeight + rerankScore * rerankWeight;
// 即  score = (原始 fusedSignal) × 0.3 + rerankScore × 0.7
```

**问题来了**：

| 场景 | score 范围 | 含义 |
|---|---|---|
| 有重排 + 命中强 | 0.5-1.0 | 0.7×高rerank + 0.3×高原始 |
| 有重排 + 命中弱 | 0.2-0.5 | 0.7×低rerank + 0.3×低原始 |
| 无重排 + 命中强 | 0.0-1.0（Min-Max归一化后） | 全部依赖归一化分母 |
| 无重排 + 仅BM25 | 0.0-1.0 | BM25 IDF 截断为 0，归一化到 [0,1] |
| 纯向量，无重排 | -1.0~1.0 | cosine，但被 `Math.max(vec, 0)` 截断 |

**S2-Pre 又额外加了 0.1/0.2 的加性 bias**（hitCount 加分、currentNodeId 加分）——**这与 searchBookV2 内部归一化后的分值不协调**。

**0.6 阈值在所有场景下都未经验证**——`agent-constants.ts:11` 的注释说"低于此置信度时提前终止"，但**没有 benchmark 表明 0.6 在何种信号组合下等价于"高置信度"**。

**后果**：
- 短查询（topK=5）下，3 条命中总能找到 ≥ 0.6 的（ranking bias）
- 长查询（topK=15）下，分散到 15 条后，top-1 经常 < 0.5
- 结论：**早停概率与查询长度负相关，与结果质量不直接挂钩**

### **问题 2 (CRITICAL)：早停路径**完全丢失** S1 的 `betterQuestion` 与 `structuralAnalysis`**

**症状**：S1 花了几秒甚至十几秒分析出"用户的真正问题是 X"，但 S2-Pre 早停时**没用**这些信息。

**根因**：看 `buildEarlyStopPrompt` 的实现：

```typescript
return `${systemPrompt}\n\n基于以下检索结果回答用户问题。...`;
```

**它只接 `systemPrompt` + `blockLines` + `userQuery` + `pdfName` 4 个参数。**

`systemPrompt` 是 `buildAnalyticalSystemPrompt` 生成的——里面**有** tocSummary / scopeList / currentNodeId / userProfileSummary，但**没有**：

- ❌ **`betterQuestion` 完全没用到！**（`AnalyticalPromptContext` 接口里甚至没有这个字段）
- ❌ **`structuralAnalysis` 完全没用到！**（S1 的核心产物，深度阅读的灵魂）

**对比正常路径**：

```typescript
// buildAnalyticalUserMessage（正常路径用）
if (betterQuestion && betterQuestion !== standaloneQuery) {
  return `${historyBlock}${prevBlock}<original_query>${standaloneQuery}</original_query>
<refined_query>${betterQuestion}</refined_query>...`;
}
```

正常路径有 `<refined_query>` 区分原始 query 和 refined query——早停路径**完全没有**。

**后果**：
- S1 改写过的 query 没传到 LLM——LLM 用用户原 query 回答，可能完全偏题
- S1 推导的章节结构分析（"这本书第 3 章重点讲 X，第 7 章讲 Y"）没传到 LLM——LLM 只能看到 3 条孤立的 chunk

**证据**（看 `agent-overview.md`）：

S1 Inspectional 的核心价值是**把目录摘要变成"基于结构的提问重写"**。如果 S1 给出 `betterQuestion="作者在 X 章节如何论证 Y"` 而用户原 query 是"X 是什么"——早停时 LLM 只能看到"X 是什么"。

### **问题 3 (HIGH)：RRF 手工融合的权重 +0.1 / +0.2 与 searchBookV2 内部归一化冲突**

**症状**：第 270-279 行的 RRF 加分让排序不稳定。

**根因**：

```typescript
// analytical-pre-search.ts:271-279
let scoreA = a.result.score + a.hitCount * 0.1;
if (currentNodeId && a.result.nodeId === currentNodeId) scoreA += 0.2;
```

`a.result.score` 是 searchBookV2 的 `fusedScore`（已归一化到 [0,1] 范围）——**再加 0.3**（极端情况：5 词命中 + 当前章节），**最终 score 范围变成 [-0.2, 1.5]**。早停阈值 0.6 在这个尺度下意义模糊。

**更严重**：5 词命中同一节点的加分（+0.5）**大于** 1 词命中 + 当前章节（+0.2 + 0.1 = +0.3）——**这反直觉**。当前章节应该是最强信号（用户在读它）。

---

### **问题 4 (HIGH)：`hits.length < 2` 闸门 vs `hits[1]?.score ?? 0` 的"零分等价"陷阱**

**症状**：当只有 1 条预检索结果时，wScore 计算被"零填充"假装有 3 条。

**根因**：

```typescript
// 第 312-314 行
const wScore = hits[0].score * 0.6
  + (hits[1]?.score ?? 0) * 0.3  // ← 0 等价于"高质量命中"
  + (hits[2]?.score ?? 0) * 0.1;

// 第 284-287 行
if (!Array.isArray(preResults) || preResults.length < 2) {
  return emptyPreSearchResult(finalScopeNodeIds);  // ← 早停闸门要求 ≥ 2
}
```

**矛盾**：
- **闸门**：`preResults.length < 2` → 不早停（走 ReAct）
- **wScore 计算**：`hits[1]?.score ?? 0` → 假设有 3 条

实际如果 `preResults.length === 2`（恰好 2 条），`hits[2]` 是 undefined，`hits[2]?.score ?? 0` 算成 0，**wScore 偏低**——**但闸门已经通过了**。结果是：2 条结果能"过关"早停，但 wScore 被打折 → 实际触发概率比预期低。

---

### **问题 5 (MEDIUM)：早停返回 `analysisResult` 后，路由层把它当 final answer 信任**

**症状**：早停时返回 `analysisResult: verifyResult.content`，但 `verifyResult.content` 只做了**链接清理**，没做**事实核查**。

**根因**：看 `verifyAndCleanContent`（`self-verification.ts:232-307`）——它只做 3 件事：

1. 提取 wiki 链接
2. 对照 `toolResults` 查 blockId 和 fileName 有效性
3. 超过 30% 是幽灵引用时调 LLM 重新生成

**问题**：
- **它不验证"内容是否真的有依据"**——LLM 可以自信地说"作者主张 X"并附一个真实的 block_id，但 block 里的内容可能不支持 X
- **cleanup 阈值 `GHOST_REF_RATIO_THRESHOLD` 是 0.3**——**4 个链接错 2 个才触发 LLM 修正**（50% 错率才警觉），实际 [INFERENCE] 较宽松
- **修正是"删幽灵 block_id"**——把 `[[file#^ghost|alias]]` 降级为 `[[file|alias]]`，**这反而丢失了"哪里说的"信息**

**额外问题 [INFERENCE]**：早停路径调用 `verifyAndCleanContent(directContent, preSearchRecords)` **不传 `options.llmClient`**——所以即使 ghost 引用超 30% 也不会触发 LLM 修正。幽灵引用被静默降级为文件级链接，**用户/下游 formatter 看不到这个降级**。

**后果**：
- 早停路径的"质量守卫"是链接形式上的，不是事实层面的
- LLM 说"作者主张 X"附了一个真实但内容无关的 block——**链接看起来对，内容是错的**
- 早停路径的降级是**静默的**——S4 收到的 `analysisResult` 看不到"链接被降级"的信号

---

### **问题 6 (MEDIUM)：实质分数 `SUBSTANTIVE_THRESHOLD = 30` 的校准基准未知**

**症状**：第 335-336 行 `SUBSTANTIVE_THRESHOLD = 30` 是硬编码。

**根因**：

```typescript
// 318-336
function computeSubstantiveScore(): number {
  if (hits.every(h => h.matched_blocks.every(b => !b.block_id))) {
    return 0;  // 纯标题回退
  }
  let maxScore = 0;
  for (const h of hits) {
    for (const b of h.matched_blocks) {
      let s = 0;
      if (b.block_id) s += 20;                          // 有 block_id
      s += Math.min(b.content.length / 10, 30);         // 文本长度（封顶 30）
      if (b.content.length > 20) s += 15;               // 非空壳
      maxScore = Math.max(maxScore, s);
    }
  }
  return maxScore;
}
```

**最大分值**：20 + 30 + 15 = 65。
**阈值 30** → 意味着至少需要 `block_id + 100 字内容` 或 `block_id + 30 字内容 + 非空壳`。

**问题**：
- `content.slice(0, 200)`（第 296 行）——所有 chunk 都被截到 200 字 → 最长 30 + 15 = 45 分
- 实际"满分"是 65，**永远拿不到**
- 阈值 30 是"中等截断"——**但 200 字截断下 30 分相当于"100 字 + block_id"**——这与"实质"的直觉不完全一致

## 三个隐性 bug (hidden)

> 不是早停决策本身的 bug，但**影响 S2-Pre 整体行为**。

### **A. `extractCitedNodeIds` 的 ARROW 模式过宽**

```typescript
// chapter-reference-parser.ts:24
const ARROW_BARE_PATTERN = /[—–-]\s*(\d+)\s*[-–—]/g;
```

任何形如"— 1234 —"的数字都被识别为章节引用（前后都有破折号）。问题是：

- "GDP 增长率 — 5% — 创下新高" → 匹配 `— 5 —` 引用章节 0005
- "页码 12 — 35" → 匹配 `— 35` 没有后破折号，不命中
- **误报：用户消息里所有"— 数字 —"都被当作章节引用**

**后果**：`currentNodeId` 强制进入 scope 时夹杂**完全无关的章节**——**scope 变臃肿** → searchBookV2 Stage 4 零召回回退触发 → scope 失效。

### **B. `validateScopeNodeIds` 失败时**用空 validIds 继续走

```typescript
// analytical-pre-search.ts:90-93
} catch (err) {
  log('[S2-Pre] Scope validation failed, using all IDs:', err);
  return { validIds: scopeNodeIds, nodeFileMap: {} };
}
```

**读 tree.json 失败**时（vault 损坏、文件被锁、Electron 路径权限），**直接信任 S1 给的所有 nodeId**——但这些 id 可能根本不存在！`nodeFileMap` 设为 `{}` 下游 LLM 无法用 wiki 链接。

**修复方向**：失败时**强制走 ReAct** 而不是带坏 scope 走早停。

### **C. `enforceScopeHardGuard` 的 `llmExclusionReason` 字段是死代码**

`ScopeHardGuardResult.injected[].llmExclusionReason` —— `enforceScopeHardGuard` 接受 `llmExclusionReason` 参数，但**只有 `current` 类型的 injected 才会用**。而 `preSearchNode` 调它时**没传**这个参数：

```typescript
// preSearchNode 第 154 行
const guardResult = enforceScopeHardGuard(
  validatedScopeNodeIdsRaw,
  currentNodeId,
  citedFromMessages,
  // ← 没传第 4 参数 llmExclusionReason
);
```

S1 Inspectional 也没传——所以这个字段**永远是 undefined**，没起到"记录 LLM 拒绝原因"的作用。

## 建议的修复路径 (future)

> 按"修复成本 / 收益"从高到低排序。

### **第一优先级 (Critical) — 必做**

1. **Bug 2 修复**：扩展 `buildEarlyStopPrompt` 接受 `betterQuestion` + `structuralAnalysis`，在 prompt 里注入 `<refined_query>` / `<book_structure>` 块。
2. **Bug 4 修复**：把 wScore 计算改为"按实际可用 slot 计入权重并归一化"——消除零填充陷阱。
3. **Bug 5 修复**：早停路径调用 `verifyAndCleanContent` 时**传 `mainModel` 作为 `llmClient`**（需要把 LangChain ChatModel 适配为 `{ chat: Function }` 形态）；或者作为**降级方案**：当 ghost 引用超阈值时，**在 cleanedContent 顶部加 `[⚠️ 来源核验]` 警告**让 S4 可见。

### **第二优先级 (Threshold) — 应该做**

4. **Bug 1 修复**：分场景定义阈值——`rerankerRole` 存在时用 `rerankScore`（0-1 含义清晰），否则用 `fusedScore / maxFusedScore` 归一化。
5. **Bug 3 修复**：RRF 加性 → 乘性——`scoreA = a.result.score * (1 + Math.log(hitCount)); if (currentNodeId) scoreA *= 1.3`。
6. **Bug 6 修复**：注释化 `SUBSTANTIVE_THRESHOLD = 30` 的语义（"block_id 20 + 100字内容 10"）或重新校准（content 截断从 200 提到 500）。

### **第三优先级 (Polish) — 可选**

7. **Bug 5 增强**：早停返回前，调便宜 LLM 判 "claim 是否被该 block 支撑"（Yes/No）——不支撑的链接降级 + 加 [来源未核验] 标记。
8. **隐 bug A 修复**：`extractCitedNodeIds` 的 ARROW 模式加白名单（只在章节标题上下文匹配）。
9. **隐 bug B 修复**：`validateScopeNodeIds` 失败时强制走 ReAct。
10. **隐 bug C 清理**：删 `llmExclusionReason` 死代码或传参。
