## 总览：Agent 检索调用链 — overview

```
用户问问题
  └─→ FrontendAgent.runGraphEngine()
        └─→ routerNode (S0)
              │
              └─→ preSearchNode (S2-Pre)
                    │ 输入: query + scopeNodeIds (来自 Inspectional)
                    │ 输出: preSearchBlock, validatedScopeNodeIds
                    │ 调用: searchBookV2()  ←  本文档主体
                    │
                    └─→ analyticalNode (S2)
                          │ 调用: searchBookV2() + 工具循环 (search_text / read_section)
                          │ 输出: analysisResult, toolResultsSnapshot
                          │
                          └─→ formatterNode (S4)
                                │ 验证: claim-verifier  ←  第四节
                                │ 输出: formattedOutput (含 [[file#^block|text]] 链接)
```

**核心调用方**（基于 codegraph 实时索引的 blast-radius 分析）：

| 调用方 | 用途 | 位置 |
|---|---|---|
| `analytical-pre-search` | S2-Pre 预检索 + 早停判断 | `src/agent/graph/nodes/analytical-pre-search.ts` |
| `analytical` | S2 主体，工具循环主入口 | `src/agent/graph/nodes/analytical.ts` |

## 8 阶段混合搜索 searchBookV2 — pipeline

**位置**：`src/pageindex/book-search-v2.ts:85`（748 行）

```
Stage 1   Dynamic recall K     按 query 长度决定 K（短/中/长 → 50/30/15）
Stage 2-3.5  并行三路召回      BM25 + 向量 + 命题
Stage 4   Scope 过滤           按 scopeNodeIds 过滤，空召回时回退
Stage 5   分数融合 + 层级加权  三路分数 Min-Max 归一化后加权
Stage 6   LLM 树搜索           (TODO: 等待 llmClient 接入)
Stage 7   Cross-encoder 重排   读 top-20 原文（1500 字符）调 rerank
Stage 8   匹配块定位           proposition > chunkHits > bm25 node text
```

### Stage 1：动态召回数 K

```typescript
// src/pageindex/book-search-v2.ts:401
function computeDynamicRecallK(query: string): number {
  if (query.length < 5)  return 50;
  if (query.length <= 15) return 30;
  return 15;
}
```

`scopeNodeIds` 存在时 K 放大 5 倍——S1 已经缩小过范围，可以让 K 放心放大。

### Stage 2-3.5：并行三路召回

| 信号 | 来源 | 触发条件 |
|---|---|---|
| BM25 | `bm25.json` | 始终 |
| 向量 | `vectors.jsonl`（L2 chunks，缺则回退 L1） | `embedding.provider !== 'local'` |
| 命题 | `prop-vectors.jsonl` | 同上 |

**Query embedding 预计算一次**（Stage 1 后，Stage 2-3.5 共享），避免每个召回器各自调一次。

```typescript
const [bm25Results, vectorSearchResult, propSearchResult] = await Promise.all([
  searchBM25(query, bm25Index, expandedK),
  precomputedEmbedding
    ? asyncVectorSearch(indexDir, precomputedEmbedding, expandedK, app)
    : Promise.resolve({ scores: new Map(), chunkHits: new Map(), vector: null }),
  precomputedEmbedding
    ? asyncPropositionSearch(indexDir, precomputedEmbedding, expandedK, app)
    : Promise.resolve(new Map()),
]);
```

### Stage 4：Scope 过滤

`scopeSet.has(id)` 过滤；**过滤后空集合回退到未过滤**——避免 S1 选错 scope 时零召回：

```typescript
if (scopedCandidates.size > 0) {
  candidateNodeIds = scopedCandidates;
} else {
  piLog(`[book-search-v2] Scope filter produced 0 results from ${allNodeIds.size}, using unscoped fallback`);
}
```

### Stage 5：分数融合 + 层级加权

**自适应权重**：

| 条件 | 向量 w_v | BM25 w_b | 命题 w_p |
|---|---|---|---|
| 有向量 + 有命题 | 0.5 | 0.25 | 0.25 |
| 有向量 + 无命题 | 0.7 | 0.3 | — |
| 无向量 | — | 1.0 | — |

各信号 **Min-Max 归一化**后加权求和（cosine 相似度可能为负，先 `Math.max(vec, 0)` 截断）：

```typescript
fusedScore = w_v * normalizedVec + w_b * normalizedBM25 + w_p * normalizedProp;
```

**层级加权**（`computeLevelWeightFast` 走预构建 treeIndex，O(1) 查询）：

| 层级 | 权重 |
|---|---|
| depth=0 (书级) | 1.0 |
| 有子节点 (章级) | 0.9 |
| 叶节点 (节级) | 0.7 |

最终 `fusedScore × levelWeight` 作为排序键。

### Stage 6：LLM 树搜索

```typescript
// TODO: implement when llmClient is available
```

**占位阶段**，未来接 LLM 在树上做语义搜索（替代或增强三路召回）。
设计上是给"用户问题很模糊，三路召回都不灵"的情况兜底——LLM 在树结构上做几轮确认/展开。

### Stage 7：Cross-encoder 重排

- 读取 top-N（默认 20）候选的 Markdown 原文（前 1500 字符）
- 调 `crossEncoderRerank()` rerank API（POST `{baseUrl}/rerank`）
- 融合：`finalScore = rerankWeight × rerankScore + (1 - rerankWeight) × fusedScore`
- 默认 `rerankWeight = 0.7`
- **失败兜底**：rerank 不可用时回退到原 fusedScore（用原 fusedScore 填充 rerankScores，保证后续 `fusedScore` 计算不会变 NaN）

**目录重命名兼容**：`resolveExportDirName()` 在重排前扫描 `DeepReader/` 目录找 `tree.json.nodeFileMap` 实际指向的文件，处理用户重命名书籍目录的情况。

### Stage 8：匹配块定位

详见 [匹配块定位 matchedBlocks](#matchedblocks-blocks) 章节。

## BM25 检索算法 — bm25

**位置**：`src/pageindex/bm25.ts:126`

### 分词策略

`tokenize()` 对不同文本采用不同策略：

| 文本类型 | 策略 |
|---|---|
| CJK 文本 | unigrams + bigrams + 完整词组（**保留重复**以支持词频） |
| 英文/数字 | 空格分词 + 小写化 |

```typescript
// 关键：不去重，BM25 依赖 TF（词频）
tokens.push(cjk);              // 完整词组
for (let i = 0; i < cjk.length; i++) tokens.push(cjk[i]);  // unigrams
for (let i = 0; i < cjk.length - 1; i++) tokens.push(cjk.slice(i, i+2));  // bigrams
```

### 评分公式

```
IDF(t) = max(0, log((N - df(t) + 0.5) / (df(t) + 0.5)))
BM25(d, t) = IDF(t) × (tf(d,t) × (k1+1)) / (tf(d,t) + k1 × (1 - b + b × |d|/avgdl))
score(d, q) = Σ_{t ∈ q} BM25(d, t)
```

参数：`k1 = 1.5`, `b = 0.75`，`IDF` 下限夹紧为 0（高频词 > 50% 文档时无判别力）。

### 查询时过滤

`filterQueryTokens()` 去除 CJK 停用词（的/了/是/在/我/有/和/就/不/人/都/一 40+ 个）并去重——**索引构建时不去重**（要 TF），**查询时去重**（避免重复累加）。

### `searchBM25Light()` 轻量版

**位置**：`src/pageindex/proposition-search.ts:173`

命题搜索专用，只读必要字段：
- 跳过 `treeData.structure` 完整加载（只取 `nodeFileMap`）
- 跳过父节点路径信息（命题卡自带 `sourceNodeId`）
- 适合大批量命题并行的内存敏感场景

## 向量检索（chunk 余弦） — vector

**位置**：`src/pageindex/book-search-v2.ts:485` (`asyncVectorSearch`)

### 数据源

- 主：`vectors.jsonl` 中的 `level: "L2"` chunk
- 兜底：无 L2 结果时（老索引格式）回退到 `level: "L1"`
- 调用 `cosineSearchJsonl()` 做流式余弦相似度

### 流程

```typescript
// L2 召回（over-recall 3x，因为多 chunk 共享 nodeId）
const vectorResults = await cosineSearchJsonl(vectorsPath, queryVector, topK * 3, { level: "L2" });

// 兜底到 L1
if (vectorResults.length === 0) {
  const l1Results = await cosineSearchJsonl(vectorsPath, queryVector, topK, { level: "L1" });
  vectorResults = l1Results.map(r => ({ ...r, blockIds: [] }));
}

// 聚合：同一 nodeId 取最大 score
for (const r of vectorResults) {
  scores.set(r.nodeId, Math.max(prev, r.score));
  if (r.blockIds.length > 0) chunkHits.get(r.nodeId)!.push({ chunkId, blockIds, score });
}
```

### 失败兜底

抛异常时返回空 scores map，Stage 5 自适应权重自动把 w_v 设为 0（切到纯 BM25 路径）。

### `chunkHits`

聚合同一 nodeId 下所有匹配的 chunk，**每个 chunk 携带 `blockIds[]`**，是 Stage 8 定位 matchedBlocks 的关键输入。

## 命题检索（独立通道） — proposition

**位置**：`src/pageindex/proposition-search.ts`

命题卡片（`propositions.json` + `prop-vectors.jsonl`）是**独立于 chunks 的检索通道**：
索引构建时给每张卡生成 embedding，检索时走专用通道与 BM25/向量并列。

### `searchPropositions`（向量通道）

```typescript
// src/pageindex/proposition-search.ts:58
export async function searchPropositions(
  query, bookId, vaultPath, embedding, topK = 5, app?
): Promise<PropositionMatch[]>
```

- 加载 `propositions.json` + `prop-vectors.jsonl`
- query → embedding → 遍历所有卡向量做 cosine
- 过滤 `score > 0.3` 的卡
- 按 `sourceNodeId` 聚合返回

### `loadPropositions` / `loadPropVectorStore`

低层加载器，**支持 vault adapter**（移动端用 `app.vault.adapter.read`，桌面端用 `fs.readFile`）——这是搜索层跨设备兼容的关键。

### `formatPropositionResults`

把命题结果格式化成 LLM 友好的文本：

```
【definition】纳瓦尔宝典的核心主张是...

原文：纳瓦尔宝典强调...
关键词：财富、杠杆、判断力
```

### `asyncPropositionSearch`（`searchBookV2` 内部用）

与 `searchPropositions` 接口类似但**返回 Map<nodeId, PropositionCard[]>**（按章节聚合，给 Stage 8 定位用）。

## 跨书籍融合 searchWithPropositions — fusion

**位置**：`src/pageindex/proposition-search.ts:106`

**用途**：跨书搜索（S3 节点使用）—— 给定一个查询，**同时**用命题 + BM25 在多本书上召回，再按 `sourceNodeId` 聚合成跨书节点。

### 流程

```typescript
const [propResults, bm25Results] = await Promise.all([
  searchPropositions(query, bookId, vaultPath, embedding, topK * 2, app),
  searchBM25Light(query, indexDir, topK * 2, app),
]);

// 按 nodeId 合并
for (const match of propResults) {
  const nodeId = match.card.sourceNodeId;
  const entry = nodeMap.get(nodeId) ?? newEntry;
  entry.matchedCards.push(match);
  entry.vectorScore = Math.max(entry.vectorScore, match.score);
}

for (const bm25 of bm25Results) {
  const entry = nodeMap.get(bm25.nodeId) ?? newEntry;
  entry.bm25Score = Math.max(entry.bm25Score, bm25.score);
  if (!entry.title) entry.title = bm25.title;  // 优先用 BM25 的 title（更准确）
}

// 融合
entry.fusedScore = weights.prop * entry.vectorScore + weights.bm25 * entry.bm25Score;
```

**默认权重** `prop: 0.6, bm25: 0.4`——命题比 BM25 略高，因为命题卡本身就是 LLM 提炼的事实，匹配精度更高。

### 返回结构 `FusionResult`

```typescript
{
  nodeId: string;
  title: string;          // 从 BM25 来（命题卡不带 title）
  fileName: string;       // 用于 wiki 链接
  matchedCards: PropositionMatch[];  // 该 node 命中的命题卡
  bm25Score: number;
  vectorScore: number;
  fusedScore: number;
}
```

## 跨书籍搜索 syntopical — cross-book

**位置**：`src/agent/utils/syntopical-search.ts`（3 调用方之一：`syntopical` node）

**场景**：用户问"这些书都在讲 X，有什么共同点？"——需要**多书并列检索** + 跨书融合。

### 流程

1. 调 `scanIndexedBooks()` 扫描 `pageindex/` 拿到所有 bookId
2. 并行对每本书调 `searchWithPropositions()`（prop + BM25 融合）
3. 把多书的 `FusionResult[]` 合并到统一的 node list
4. 按 `fusedScore` 全局排序，截 topK
5. 注入到 prompt 让 LLM 跨书比较

### 与 `searchBooks`（WeRead）区别

`searchBooks` 是**微信读书远程 API 搜索**（`src/weread/api/client.ts:119`），
是 S-Advisor 在无书模式下的兜底——**不读本地索引**，而是搜用户的微信读书书架。

| 维度 | syntopical（本地） | searchBooks（WeRead 远程） |
|---|---|---|
| 数据源 | 本地 PageIndex 索引 | 微信读书 API |
| 适用 | 已索引的本地书 | 任意微信读书上的书 |
| 返回 | `FusionResult[]`（含 nodeId） | `WereadSearchBook[]`（含 bookInfo） |
| 触发 | S3 Syntopical 节点 | S-Advisor 节点 |
| 工具 | 内部调用 | LangChain 工具 `search_read_books` |

## Cross-encoder 重排 — rerank

**位置**：`src/pageindex/book-search-v2.ts:663` (`crossEncoderRerank`)

### 流程

```
fused top-20 候选
  │
  ├─ resolveExportDirName()  ←  处理用户重命名书籍目录
  │
  ├─ 读每本书的 Markdown 原文（前 1500 字符，去 frontmatter）
  │
  ├─ POST {baseUrl}/rerank
  │   {
  │     model: "BAAI/bge-reranker-v2-m3",
  │     query,
  │     documents: texts,
  │     top_n: texts.length,
  │   }
  │
  └─ 融合到 fusedScore
```

### Provider 支持

| Provider | baseUrl | apiKey |
|---|---|---|
| `lmstudio`（默认） | `http://localhost:1234/v1` | `"lm-studio"` |
| `ollama` | `http://localhost:11434` | — |
| 其他（openai 兼容） | 用户配置 | 用户配置 |

### 失败兜底

Rerank API 不可用时，**用原 fusedScore 填充 rerankScores**：

```typescript
} catch (error) {
  piLog(`[book-search-v2] Reranker unavailable: ${error}`);
  for (let i = 0; i < nodeIds.length; i++) {
    rerankScores.set(nodeIds[i], results.find(r => r.nodeId === nodeIds[i])?.fusedScore || 0);
  }
}
```

→ 后续 `fusedScore = rerankWeight × rerankScore + (1 - rerankWeight) × fusedScore` 自然退化为
`fusedScore × 0.7 + fusedScore × 0.3 = fusedScore`（无副作用）。

## 匹配块定位 matchedBlocks — blocks

**位置**：`src/pageindex/book-search-v2.ts:333-368`

把 `searchBookV2` 的最终结果映射到**段落级**（聚焦到 `^block_id`），让 LLM 输出可以插入 `[[file#^block|text]]` 链接。

### 三级优先级

1. **命题卡片**（最多 3 张）
   ```typescript
   matchedBlocks = matchedCards.slice(0, 3).map(card => ({
     blockId: card.id,
     content: `${card.context} ^${card.id}\n\n【${card.type}】${card.answer}`,
   }));
   ```

2. **向量 chunkHits**（最多 3 个）
   ```typescript
   matchedBlocks = chunks.slice(0, 3).map(c => ({
     blockId: c.blockIds[0] ? `^${c.blockIds[0]}` : "",
     content: chunkTextMap.get(c.chunkId) || "",
   }));
   ```

3. **BM25 节点文本**（**排除 calibre-pb-*** 假 block ID）
   ```typescript
   const blockIdMatches = [...text.matchAll(/\^([\w-]+)/g)];
   const blockId = blockIdMatches.find(m => !/^calibre-pb-\d+$/.test(m[1]))?.[1] ?? "";
   matchedBlocks = [{ blockId, content: text.slice(0, 300) }];
   ```

4. 兜底：`[{ blockId: "", content: "【${title}】" }]`

### `calibre-pb-*` 排除

Calibre 导出的 EPUB 用 `calibre-pb-{N}` 当分页符，**不是真正的 Obsidian block ID**。
正则 `!/^calibre-pb-\d+$/` 排除这些假 ID，只保留真正的 `^xxx` block_id。

### `chunkTextMap`

按需加载 `chunks.jsonl`（通过动态 `import("./vault/vectors.js")` 避免循环依赖），构造 `chunkId → text` 的 Map 给 Stage 8 查文本。

## Claim 验证 claim-verifier — claims

**位置**：`src/agent/graph/utils/claim-verifier.ts`

**位置**：formatter 节点前的一道关卡，验证 LLM 在 S2/S4 输出的"事实主张"（claim）是否真的有书内段落支撑。

### 流程

1. 解析 LLM 输出，提取所有 `[[file#^block|text]]` 链接
2. 调 `searchBookV2()` 重新搜这些 claim 的原段落
3. 比对：
   - 链接的 `file#^block` 是否真在 tree.json 的 nodeFileMap 里
   - 链接的 block 文本是否在 LLM 输出中被准确引用（不被截断/篡改）
4. 不通过：
   - 把不通过的 claim 标记为 "unverified"
   - 在 S4 输出中插入 `[来源未核验]` 警告
   - 触发 `correctionDetected` 状态让 S2 重跑

### 调用方

- `formatterNode` —— 最终输出前最后一道门
- 也被 `analytical-pre-search` 用来做"早停判断"——如果 LLM 自称搜到了某内容但 claim-verifier 找不到证据，就**强制跑 S2 不让早停**。

## 书籍 ID 解析：跨设备 fallback — resolver

**位置**：`src/pageindex/book-resolver.ts`

`resolveBookIdFromPdf(app, pdfName)` 解决"在搜索时只知道书名，怎么找到 bookId？"的问题。

### 桌面端（有 basePath）

```typescript
const basePath = app.vault.adapter.basePath;
const bookFile = app.vault.getFiles().find(f =>
  f.path.includes(pdfName.replace(/\.pdf$|\.epub$/, ''))
  && (f.extension === 'pdf' || f.extension === 'epub')
);
return sha256Hex(`${basePath}/${bookFile.path}`).slice(0, 8);
```

直接用绝对路径哈希，与索引构建时的 bookId 一致。

### 移动端（无 basePath）

遍历 `pageindex/` 下所有 bookId 目录，读 `book-meta.json` 匹配 `title` 字段。
**移动端必须靠 title 模糊匹配**（无文件系统绝对路径）。

### 调用点

- `src/agent/graph/utils/tree-loader.ts`（Agent 启动时）
- `src/agent/tools/local/search-text.ts`（`search_markdown_text` 工具）
- `src/agent/tools/local/utils.ts`（其他本地工具）

## 性能优化缓存 — cache

**位置**：`src/pageindex/book-search-v2.ts:54`

```typescript
const indexCache = new Map<string, { data: any; ts: number }>();
const INDEX_CACHE_TTL = 60_000;  // 1 分钟

function getCached<T>(key: string, loader: () => Promise<T>): Promise<T> {
  const cached = indexCache.get(key);
  if (cached && Date.now() - cached.ts < INDEX_CACHE_TTL) {
    return cached.data as Promise<T>;
  }
  const promise = loader();
  promise.catch(() => indexCache.delete(key));  // 失败时清除
  indexCache.set(key, { data: promise, ts: Date.now() });
  return promise;
}
```

**用法**：

```typescript
// tree.json 缓存
const treeData = await getCached(`tree:${indexDir}`, () => loadTreeJson(indexDir, app));

// bm25.json 缓存
const bm25Index = await getCached(`bm25:${indexDir}`, async () => { ... });
```

**效果**：用户在多轮对话中反复搜同一本书时，**第二轮起的 tree/bm25 读取直接命中内存**，省去 fs I/O + JSON parse。

## 风险与待办 — issues

> 以下基于 codegraph 静态扫描，标 [INFERENCE] 表示未做运行验证。

- **`searchBookV2` 核心函数无单测** [INFERENCE]：6 个调用方都依赖它，但只有 `book-search-v2.test.ts`（621 行）覆盖了主流程，边界 case（scope 过滤零召回、rerank 不可用、向量 provider='local'）覆盖密度低。
- **Stage 6 LLM 树搜索** [INFERENCE]：占位阶段，设计意图是"用 LLM 在树结构上做几轮确认"，但 `llmClient` 注入协议未定义。
- **`crossEncoderRerank` 失败时静默回退** [INFERENCE]：用 `piLog` 而非 `throw`，调用方很难知道重排是否生效。
- **`asyncVectorSearch` 的 L2 → L1 回退** [INFERENCE]：当 chunks 没建 L2 但有 L1 时静默回退，UI 无法告知用户"这次搜索质量可能下降"。
- **`searchWithPropositions` 跨书融合无单测** [INFERENCE]：权重、聚合逻辑全靠人工验证。
- **`claim-verifier` 无单测** [INFERENCE]：是 Agent 输出正确性的最后一道门，逻辑复杂（解析 claim / 搜原段落 / 比对文本）。
- **`hasDiagramIntent` 永远返回 `false`** [INFERENCE]：见 [系统鸟瞰.md](./系统鸟瞰.md) 风险章节，与搜索无关但同源。
- **跨设备 resolver 移动端 title 匹配可能撞车** [INFERENCE]：如果用户有两本名字相近的书，移动端 `book-meta.json.title.includes(bookTitle)` 会误匹配第一个。
