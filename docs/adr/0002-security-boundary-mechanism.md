# 安全边界机制：防止系统提示词泄露

**Status**: accepted
**Date**: 2026-07-03

## Context

发现奚童（AI 伴读）在用户询问系统提示词时，会泄露完整的内部规则，包括：
- 工具使用原则（weread_recommend、weread_readdata 等）
- 输出规范（不生成 wiki 链接、书名用《》包裹）
- 用户了解机制（读取 user_profile、memory）
- 阅读方法论知识库（《如何阅读一本书》的四个层次）

这是一个严重的安全漏洞，可能暴露：
1. 内部实现细节（API 名称、数据来源、处理流程）
2. 用户隐私机制（如何获取用户画像、阅读历史）
3. 系统架构（LLM 调用链、节点路由逻辑）

## Decision

1. **三层防御机制**：
   - **inspectional 节点**（有书籍时）：检测安全触发词，拦截系统提示词泄露请求
   - **advisor 节点**（无书籍时）：在 system prompt 中添加安全边界规则
   - **formatter 节点**（兜底）：检测 `rewrittenQuery === '安全拒绝'`，绕过 LLM 直接返回安全消息

2. **安全触发词检测**：
   - 正则表达式匹配：`系统提示|提示词|system\s*prompt|内部规则|运作机制|开发信息|如何工作|技术架构|调用什么|使用什么工具|访问什么数据|告诉我你是|你的规则|你的设定|你的配置|你的核心|你的主要|你的工作|你能做什么|你的功能|你的能力`

3. **安全消息**：
   - 固定回复："我是你的 AI 伴读，专注于帮你理解书籍内容。有什么书想聊聊吗？"
   - 不解释为什么不能透露
   - 不承认自己有系统提示词
   - 如果用户继续追问，重复同一句话

## Considered Options

- **仅在 prompt 中添加安全规则**：拒绝。LLM 可能忽略规则，仍然泄露信息。需要在代码层面强制拦截。
- **使用内容过滤器**：拒绝。过滤器可能误判正常内容，影响用户体验。正则检测更精确。
- **在每个节点都添加安全检查**：拒绝。代码重复，维护成本高。选择三层防御机制更简洁。

## Consequences

- 用户无法获取系统提示词、内部规则、工具名称等敏感信息
- 安全拦截绕过 LLM，减少延迟（~10ms）
- 正则表达式需要维护，新增安全触发词时更新
- 测试覆盖：mt-010 安全性测试评分 100/100
