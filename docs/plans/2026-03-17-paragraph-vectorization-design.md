# 段落向量化设计方案

> 创建日期: 2026-03-17
> 状态: 待实现

## 背景

当前系统仅对**章节摘要**进行向量化，用户提问时只能定位到章节级别。本设计新增**段落向量化**，支持精确到段落的检索和引用。

## 目标场景

1. **精确检索** - 用户提问时，能定位到具体的段落而非整个章节
2. **上下文增强** - 段落向量 + 章节摘要向量组合，提供更丰富的检索结果
3. **细粒度阅读** - 支持"跳转到相关段落"功能，帮助用户快速定位内容

## 核心设计决策

| 决策点 | 选择 | 说明 |
|--------|------|------|
| 段落定义 | 物理段落 | PDF 中原本的换行分隔的段落 |
| 存储方式 | 同一 Collection | 段落和章节摘要存在同一个 collection，通过 `metadata.type` 区分 |
| 检索策略 | 由 LLM 决定 | 返回原始混合结果，让 Agent 根据问题类型自行判断 |
| 短段落处理 | 保留全部 | 即使很短也单独向量化，不合并不过滤 |
| Chunk 大小 | 300-400 字 | 按句子边界切分，硬性上限 500 字 |
| 块标识 | 章节前缀式 | 如 `^ch1-p3`（第1章第3段），便于人工理解 |

## 数据模型

### 段落 Chunk 结构

```python
{
  "id": "idx_xxx_ch1-p3-c2",        # 向量库内部 ID（区分 chunk）
  "text": "chunk 的部分文本...",     # 用于向量化的文本（300-400字）
  "metadata": {
    "type": "paragraph",            # 区分类型：paragraph / section
    "block_id": "^ch1-p3",          # Obsidian 引用标识（段落级别，同一段落的多个 chunk 共享）

    # 完整段落内容（用于返回给前端/Obsidian 引用）
    "full_paragraph": "完整的段落原文...",

    # Chunk 信息（仅用于向量检索）
    "chunk_index": 2,               # 该段落内的 chunk 序号
    "total_chunks": 3,              # 该段落总 chunk 数

    # 层级关联
    "parent_node_id": "node_5",     # 所属章节 ID
    "parent_section": "第一篇 > 第一章",  # 章节路径

    # 位置信息
    "page": 15,                     # 所在页码
    "paragraph_index": 3,           # 章节内段落序号

    # 文档信息
    "pdf_name": "书名"
  }
}
```

### 与章节摘要的对比

| 类型 | type | 粒度 | 数量级 | 用途 |
|------|------|------|--------|------|
| 章节摘要 | `section` | 章节 | ~10-50 | 提供宏观上下文 |
| 段落原文 | `paragraph` | 段落 | ~100-500 | 精确检索定位 |

## 切分算法

### 参数配置

| 参数 | 值 | 说明 |
|------|-----|------|
| 目标最小 | 300 字 | 尽量达到的最小长度 |
| 目标最大 | 400 字 | 理想的切分点 |
| 硬性上限 | 500 字 | 超过则强制切分 |
| 最小保留 | 100 字 | 小于此值不切分 |

### 切分规则

```
1. 按句子分割（中文句号、问号、感叹号：。！？）
2. 贪心合并：逐句累加，达到 300 字后检查句末
3. 边界优先：300-400 字之间遇到句末就切分
4. 强制切分：超过 500 字且无句末，在最近逗号处切分
```

### 切分示例

```
段落原文（1200 字）：
"第一句（100字）。第二句（200字）。第三句（300字）。第四句（250字）。第五句（350字）。"

切分结果：
├── chunk 1: 第一句 + 第二句 + 第三句 = 600 字 → 回退，第一句+第二句=300 字 ✓
├── chunk 2: 第三句 + 第四句 = 550 字 → 第三句=300 字 ✓
└── chunk 3: 第四句 + 第五句 = 600 字 → 第四句=250 字（太短，合并第五句）→ 600 字（可接受）
```

### 特殊情况处理

| 情况 | 处理方式 |
|------|----------|
| 段落 < 100 字 | 不切分，直接作为一个 chunk |
| 单句 > 500 字 | 在逗号处强制切分 |
| 无标点的连续文本 | 每 400 字硬切分 |

## 实现流程

### 索引流程变更

```
现有流程：
PDF/EPUB → PageIndex 解析 → 提取章节 → LLM 生成摘要 → 向量化摘要 → 存入 ChromaDB

新增流程：
                                      ↓
                              提取章节内段落
                                      ↓
                              生成 block_id (^章节-段落)
                                      ↓
                              按 300-400 字切分 chunk
                                      ↓
                              向量化 chunk → 存入同一 Collection
```

### 进度条调整

```
现有：
60-85%: 生成摘要
85-90%: 存储向量数据（章节）
90-95%: 保存元数据

新增：
60-85%: 生成摘要
85-88%: 存储章节向量
88-92%: 提取并存储段落向量  ← 新增
92-95%: 保存元数据
```

## 检索与返回

### 检索逻辑

```
用户查询 → ChromaDB 向量检索（同一 Collection）
         → 返回 Top N 结果（混合章节 + 段落 chunk）
         → 透传给 Agent/LLM 处理
```

### search-doc 接口返回格式

**章节结果：**
```
1. **章节名** (Page 15) (relevance: 0.85)
   Link: [[文件名|章节名]]
   node_id: node_5
   章节摘要内容...
```

**段落结果（新增）：**
```
2. **第一篇 > 第一章** (Page 15) (relevance: 0.92) [段落]
   Link: [[文件名#^ch1-p3]]
   block_id: ^ch1-p3
   段落原文内容...
```

### Obsidian 引用

当用户想引用某段内容时：
```
Obsidian 引用格式：[[书名#^ch1-p3]]
显示内容：完整段落原文（不是 chunk 片段）
```

## 风险与考虑

1. **向量数量增加** - 段落数量远大于章节数，需关注检索性能
2. **存储空间** - 需要额外存储 `full_paragraph` 字段
3. **向后兼容** - 旧索引无段落向量，检索时仅返回章节结果
